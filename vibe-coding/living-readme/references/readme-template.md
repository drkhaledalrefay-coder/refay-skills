# README template — section skeleton and guidance

Copy this order. Each section has one line of guidance. Delete anything marked
`[optional]` that does not apply, and never keep an empty heading.

Which sections matter by project type (`R` = required, `o` = optional, `—` = drop):

| Section | Library | Web app | CLI | Data / research |
|---|---|---|---|---|
| 1 Header + badges | R | R | R | R |
| 2 Opening (audience split) | R | R | R | R |
| 3 What it is / is not | R | R | R | R |
| 4 What's inside | o (API surface) | R (modules) | o (commands) | o (datasets) |
| 5 How it works | o | R | R | R (pipeline) |
| 6 Screenshots | — | R | o (terminal) | o (charts) |
| 7 Status & honest limits | R | R | R | R |
| 8 Languages (human + code) | o | o | o | o |
| 9 Getting started | R | R | R | R |
| 10 Quality gates | o | R | o | R |
| 11 Repo map | o | R | o | o |
| 12 How it was built | o | o | o | R (method/lineage) |
| 13 Documents & where to verify | o | R | o | R |
| 14 Lineage / licence | R | R | R | R |

**1. Header + badges.** Centered block with the real logo if `media.logo_candidates` has one; tagline under the name; only badges you can point at (workflow file exists, licence file exists, live URL confirmed by the owner). A broken badge is worse than no badge.

**2. Opening — audience split.** Two short blocks. *For users / business:* what it does for them, in their words, no stack names. *For developers:* the one-paragraph technical identity (language, framework, runtime, hosting, how big it is). Both must be true and both must be readable in fifteen seconds.

**3. What it is / what it is not.** Bullet list, `It IS …` / `It is NOT …`. The "is not" lines prevent the most expensive misunderstandings (not a public storefront, not microservices, not a replacement for X, not production-hardened).

**4. What's inside.** Table: `Module | Route or entry point | Who sees it | What it does | Where to verify`, where the last column is a real file path (`app/Http/Controllers/X.php`, `src/x.py`). For a library, use the public API surface instead of routes; for a CLI, the commands.

**5. How it works.** One ASCII diagram of the real flow (request path, data pipeline, build chain), then 3–6 bullets on the non-obvious decisions and safety rails. ASCII only — no image the repo cannot regenerate.

**6. Screenshots.** `[optional]` Only real captures, only if approved. Table or centered images with a caption naming the screen and the route. Never a mockup shown as the product; never a screenshot containing real customer data.

**7. Status & honest limits.** Dated (`as of YYYY-MM-DD`) status line plus a numbered list of real constraints: single-process server, no queue worker, volatile sessions, CI that does not gate deploys, untested paths, unfinished modules, known performance ceilings. This is the section that makes the rest believable — do not soften or omit it.

**8. Languages (human + programming).** `[optional]` Human languages the product supports (from the owner), then a table of programming languages with line counts and roles, copied from `facts.json languages`. Say "approximate" and say where the numbers came from.

**9. Getting started.** Copy-paste commands taken verbatim from the repo (Makefile, package scripts, CI steps, README of a subfolder). Prerequisites first, then the shortest path to a running system, then the verification command. Add a `[!CAUTION]` for destructive commands (never `migrate:fresh` on prod, no force-push).

**10. Quality gates.** `[optional]` The exact commands that must pass before a commit (`pytest`, `npm run build`, `pint --test`, `go test ./...`), plus any manual gate (check the real page at 360 px, never verify styling against raw HTML).

**11. Repo map.** `[optional]` Table `Path | Purpose`, one line each, top-level dirs from `facts.json top_level`. Keep it under ~12 rows; deeper detail belongs in `docs/`.

**12. How it was built.** `[optional]` Only with owner input: origin and start date, the human author and their role, effort/timeline numbers, AI tools used and what each did (commit trailers from `facts.json git.ai_co_author_trailers` are evidence; guesses are not), the human-governed review loop, audit/quality evidence with dates and links. Credit other people **only** after explicit owner approval.

**13. Documents & where to verify.** `[optional]` Table `Question | Document to consult`, linking real files (`docs/ARCHITECTURE.md`, `SECURITY.md`, `docs/EVALUATION.md`). This is the README's exit door: everything too long to include lives here, verified.

**14. Lineage / licence / contributing.** Where the project came from (fork, prior work, dataset), licence status and any attribution requirements, then the contribution rules: branch → PR → CI → owner review → merge, and what must never be edited by hand.

## Formats worth copying

- **Cell with two paths:** `` `app/Http/Controllers/X.php`<br>`resources/views/x.blade.php` `` — keeps the "where to verify" column honest.
- **Dated status line:** `**Status (2 Nov 2026):** …` — always a date.
- **Warning callouts (GitHub-flavoured, degrade to plain quotes elsewhere):**
  `> [!WARNING]`, `> [!CAUTION]`, `> [!IMPORTANT]`.
- **Percentages:** only if a command produced them; a routing count is not an accuracy score, and the README should say so.
- **Placeholders you must resolve or delete:** `<owner>`, `<repo URL>`, `<live URL>`, `<logo>`. A shipped `<...>` is a bug.
